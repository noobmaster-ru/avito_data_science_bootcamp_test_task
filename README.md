# Кандидатогенерация для поиска услуг Авито (тестовое задание DS Bootcamp)

По поисковому запросу (текст, локация, фильтры) нужно отобрать до 50 объявлений из корпуса в 189 212 объявлений так,
чтобы среди них оказались объявления, которые пользователь реально выбрал. Метрика: Recall@50.

## Итоговое решение в двух словах

1. **Полный скоринг корпуса на каждый запрос** двумя текстовыми моделями: BM25 по заголовку, параметрам и описанию
   и bi-encoder `intfloat/multilingual-e5-small` (косинус эмбеддингов запроса и объявления).
2. **Слияние скоров**: `bm25 / max(bm25) + exp(50 * (cos - max(cos)))`, обе части лежат в (0, 1].
3. **Множители-бусты** к скору: совпадение локации запроса и объявления, близость объявления к центроиду локации запроса,
   популярность объявления в логе кликов train. Локация даёт самый большой прирост качества. Центроид локации запроса
   считается по train как медиана координат объявлений, которые выбирали из этой локации поиска (так покрываются все
   локации бенчмарка, а не только те, где есть объявления корпуса).
4. **Реранкер LightGBM** над топ-300 кандидатов: бинарный классификатор «кандидат релевантен» на признаках скоров,
   локации, расстояния, популярности, атрибутов объявления, пересечения токенов запроса и заголовка,
   вероятности микрокатегории по тексту запроса. Топ-50 по вероятности идёт в ответ.

Всё считается локально, без внешних API. Скрипт `run.py` воспроизводит `answer.csv` целиком.

## Почему так (главные выводы EDA, подробнее в `notebooks/01_eda.ipynb`)

- Корпус бенчмарка пересекается с train по объявлениям лишь на 9,6 %, тексты запросов бенчмарка уникальны и только на 37,5 %
  встречаются в train. Поэтому «память кликов» (запрос → объявления, которые по нему выбирали) почти не помогает,
  а основа решения — текстовый поиск по всему корпусу.
- Категория поиска почти всегда одна (услуги), фильтровать по ней бессмысленно. Локация объявления совпадает с локацией
  поиска в 83 % случаев, несовпадающие обычно рядом (медиана 34 км). Отсюда мягкий буст по локации и расстоянию,
  а не жёсткий фильтр.
- Для «виденных» запросов микрокатегория почти однозначна, но классификатор текст → микрокатегория на новых запросах даёт
  около 53 % top-1, и как буст он ухудшал качество. Его вероятности используются только как признак реранкера.

## Локальная валидация

Из train случайно откладываются 8 000 строк (V) так, чтобы тексты запросов были уникальны, а доля текстов, встречающихся
в оставшейся части (A), равнялась доле бенчмарка (37,5 %). Релевантным для строки считается её объявление. Корпус
валидации = корпус бенчмарка + объявления V, то есть те же дистракторы, что в задаче. Память кликов, популярность и
дообучение строятся только на A. Метрика считается тем же кодом, что и для сабмита (`cg/metrics.py`).

## Эксперименты (Recall@50 на локальной валидации)

| Шаг | Recall@50 |
|---|---|
| BM25 (top-300) | 0,397 |
| + память кликов и добор по микрокатегориям | 0,405 |
| + буст по локации, расстоянию и популярности (пул 300) | 0,602 |
| BM25 пул 1000 / 5000 с бустами | 0,707 / 0,770 |
| Полный скоринг корпуса: BM25 + бусты | 0,790* |
| + dense e5-small (tau = 50), полный скоринг | 0,822 |
| + центроиды локаций поиска из train (покрытие запросов 84 % → 100 %) | 0,848 |
| + реранкер LightGBM над топ-300 (300 деревьев, 31 лист) | RERANK_V3 |

\* на подвыборке из 2 500 запросов; остальные числа на всех 8 000. Кросс-валидация реранкера: 2 фолда по запросам.

Что не помогло: классификатор микрокатегорий как буст (−2 п.п.), признаки памяти кликов в реранкере (±0), более крупные
модели реранкера и lambdarank (−0,5…−1 п.п.), tau ≠ 50, более сильные или слабые локационные бусты (±0,5 п.п.).

## Структура репозитория

```
run.py                 # воспроизведение answer.csv: python run.py v4
src/cg/
  config.py            # пути, seed, K, модель
  data.py, text.py     # чтение parquet (id строками), нормализация и стемминг (Snowball)
  validation.py        # сплит train → A / V, корпус валидации
  metrics.py           # Recall@k, разрез seen/unseen
  pipeline.py          # шаблоны текстов для BM25 и bi-encoder
  sources/bm25.py      # BM25 (bm25s)
  sources/dense.py     # эмбеддинги e5 с кэшем, top-k
  sources/memory.py    # память кликов и добор по микрокатегориям (использовались на ранних шагах)
  sources/microcat.py  # классификатор текст запроса → микрокатегория (признак реранкера)
  sources/tfidf_char.py# символьный TF-IDF (в финальный пайплайн не вошёл)
  boost.py             # множители: локация, расстояние до центроида, популярность
  scoring.py           # полный скоринг корпуса: BM25 + dense + бусты → топ-K и признаки
  rerank.py            # признаки и LightGBM-реранкер
  submit.py            # сборка и строгая валидация answer.csv
scripts/               # EDA и эксперименты на валидации (val_*.py, finetune.py)
notebooks/01_eda.ipynb # разведочный анализ с выводами
```

## Воспроизведение

```bash
uv sync                                   # python 3.12, зависимости из pyproject.toml
mkdir -p data && cp /path/to/*.parquet data/
PYTHONPATH=src python run.py v4           # answer.csv в корне; эмбеддинги кэшируются в artifacts/emb
```

Реранкер обучается скриптами `scripts/rerank_feats.py` и `scripts/rerank_train.py` на локальной валидации и сохраняется
в `artifacts/reranker_v1.pkl`; `run.py v3` собирает ответ без реранкера. На Apple M1 Pro полный прогон занимает около
10 минут (из них 6 минут — эмбеддинги корпуса на MPS).

## Open-source модели и библиотеки

- `intfloat/multilingual-e5-small` (Hugging Face, MIT) — bi-encoder для dense-поиска, веса скачиваются один раз.
- `bm25s`, `PyStemmer` (Snowball) — BM25 и стемминг русского.
- `sentence-transformers`, `torch` — инференс и дообучение bi-encoder.
- `lightgbm`, `scikit-learn`, `pandas`, `pyarrow`, `numpy`, `scipy`.
