# Кандидатогенерация для поиска услуг Авито

Тестовое задание DS Bootcamp. По поисковому запросу (текст, локация, фильтры) нужно отобрать до 50 объявлений из корпуса
в 189 212 объявлений так, чтобы среди них оказались те, что пользователь реально выбрал. Метрика: Recall@50.

**Результат: Recall@50 = 0,882 на лидерборде** (лучшая из четырёх попыток), 0,928 на локальной кросс-валидации.

Отправленный ответ лежит в репозитории: [`submissions/answer.csv`](submissions/answer.csv)
(md5 `4661f6f7690211300579f278d35d8004`, копия `submissions/answer_v7_rerank_ft_w2_pool500.csv`).
Команда `uv run python run.py final` собирает его заново **в тот же файл `submissions/answer.csv`** и печатает md5 для сверки.

## Как запустить

Нужны Python 3.12, [uv](https://docs.astral.sh/uv/) и три файла задания в `data/`. Всё считается локально, без внешних API;
веса `intfloat/multilingual-e5-small` скачиваются с Hugging Face один раз.

```bash
git clone <этот репозиторий> && cd avito_bootcamp_test
uv sync                                                            # окружение .venv по pyproject.toml / uv.lock
cp /path/to/{train,benchmark_queries,benchmark_items}.parquet data/
# дообученный энкодер (архив 333 МБ, в git не помещается): скачать и распаковать, команды ниже
uv run python run.py final                                         # → submissions/answer.csv  (~12 мин, из них 8 — эмбеддинги)
uv run python scripts/validate_answer.py submissions/answer.csv    # проверка формата
```

Дообученный энкодер: **https://disk.yandex.ru/d/IKtAN1DsGcLWfg** (архив `e5s_ft_v1.tar.gz`, 333 МБ, внутри папка формата
sentence-transformers). Скачать можно в браузере или из терминала через публичный API Яндекс Диска:

```bash
curl -L -o e5s_ft_v1.tar.gz "$(curl -s 'https://cloud-api.yandex.net/v1/disk/public/resources/download?public_key=https://disk.yandex.ru/d/IKtAN1DsGcLWfg' | python3 -c 'import sys, json; print(json.load(sys.stdin)["href"])')"
mkdir -p artifacts/models && tar -xzf e5s_ft_v1.tar.gz -C artifacts/models   # → artifacts/models/e5s_ft_v1/
```

Веса реранкера (1 МБ) лежат в git: `release/reranker_final.pkl`, так что после скачивания энкодера ничего обучать не нужно.

Что произойдёт при запуске `run.py final`:

| Этап | Время |
|---|---|
| чтение данных, BM25-индекс по корпусу | 1 мин |
| эмбеддинги корпуса и запросов двумя энкодерами (кэш `artifacts/emb`, считаются один раз; на CPU дольше) | 8 мин |

На той же машине результат воспроизводится побайтно (md5 совпадает; проверено). На другом железе эмбеддинги могут
отличаться в последних знаках float, из-за чего единичные кандидаты в хвосте топ-50 могут поменяться.

**Если нет возможности скачать модель** — два запасных пути:

- `uv run python run.py no_finetune` → `submissions/answer_no_finetune.csv`: та же схема с одним, исходным энкодером
  (реранкер `release/reranker_single_encoder.pkl`). Локально 0,906, на лидерборде 0,864. Нужен только исходный e5-small.
- Полное воспроизведение с нуля, включая дообучение (около 1,5 часа на Apple M1 Pro; на GPU быстрее):

## Описание решения

### Какие данные и признаки использовал и почему

EDA (`notebooks/01_eda.ipynb`) показал три факта, которые определили решение:

- корпус бенчмарка пересекается с train по объявлениям лишь на 9,6 %, тексты запросов бенчмарка уникальны и только
  на 37,5 % встречаются в train → «память кликов» (запрос → объявления, которые по нему уже выбирали) почти бесполезна,
  решать нужно текстовым поиском по всему корпусу;
- категория поиска почти всегда одна и та же (услуги, 99,99 %), флаг доставки стоит у 12 строк из 497 673 → эти поля не используются;
- локация объявления совпадает с локацией поиска в 83 % случаев, несовпадающие обычно рядом (медиана 34 км) → локация
  и расстояние работают как сильный прайор, но не как жёсткий фильтр.

Из **train** используются: пары «запрос → выбранное объявление» для дообучения энкодера; частота кликов по объявлению
(популярность); координаты выбранных объявлений в разрезе локации поиска (центроид локации запроса; покрывает все локации
бенчмарка, тогда как центроид по объявлениям корпуса покрывал лишь 84 %); пары «текст запроса → микрокатегория» для
классификатора.

**Признаки запроса**: `search_query` + текст фильтров `search_infm_params_text` (склеиваются в один текст для BM25
и энкодеров), `search_location_id`.
**Признаки объявления**: `item_title_raw` (в BM25 с весом 3), `item_infm_params_text`, `item_description_raw` (в BM25
целиком: обрезка до 300 символов стоила 3 п.п.), `item_location_id`, координаты, `item_microcat_id`, рейтинг, число отзывов,
цена, флаги скрытого телефона и запрета сообщений. Последние идут только в реранкер.

### Какие модели и алгоритмы применил

Пайплайн из трёх стадий (`run.py`, библиотека `src/cg/`):

1. **Полный скоринг корпуса на каждый запрос** тремя текстовыми моделями: BM25 (`bm25s`, стемминг Snowball);
   bi-encoder `intfloat/multilingual-e5-small` (косинус эмбеддингов запроса и объявления, префиксы `query:`/`passage:`);
   тот же энкодер, дообученный на 200 000 парах из train (MultipleNegativesRankingLoss, in-batch негативы без дубликатов
   запросов в батче, batch 64, 1 эпоха, lr 3e-5). Слияние: `bm25/max + exp(50·(cos_e5 − max)) + 2·exp(10·(cos_ft − max))`,
   все части лежат в (0, 1]. У дообученной модели косинусы контрастнее, поэтому у неё ниже температура и выше вес.
2. **Множители к скору**: `(1 + 5·[та же локация]) · (1 + 5·exp(−расстояние/100 км)) · (1 + 0,5·log(1 + клики в train))`.
   Расстояние считается до центроида локации запроса.
3. **Реранкер LightGBM** (бинарный классификатор «кандидат релевантен», 300 деревьев, 31 лист) над топ-500 первой стадии,
   28 признаков: компоненты скоров и ранг, совпадение локации и расстояние, популярность, рейтинг, отзывы, цена, длина
   заголовка, доля стемов запроса в заголовке и в параметрах, вероятность микрокатегории объявления по тексту запроса
   (TF-IDF слов и символов + логистическая регрессия), «виденность» запроса в train. Топ-50 по вероятности идёт в ответ.

Все модели open-source и запускаются локально (список в конце).

### Как проверял качество до отправки

- **Локальная валидация, имитирующая бенчмарк** (`cg/validation.py`): из train откладываются 8 000 строк (V) так, чтобы
  тексты запросов были уникальны, а доля текстов, встречающихся в оставшейся части (A), равнялась 37,5 %, как в бенчмарке.
  Релевантным для строки считается её объявление. Корпус валидации = корпус бенчмарка + объявления V (те же дистракторы,
  что в задаче). Популярность, центроиды, классификатор микрокатегорий и дообучение строятся только на A.
- **Метрика тем же кодом, что и для ответа** (`cg/metrics.py`): Recall@50, плюс Recall@100/300/500 как потолок для
  реранкера и разрез «текст запроса виден / не виден в train».
- **Реранкер** оценивается кросс-валидацией по запросам V (2 фолда), финальная модель обучается на всём V.
- **Каждая идея проверялась отдельным скриптом** (`experiments/`) на одном и том же сплите; на лидерборд отправлялись
  только версии с локальным приростом больше 1 п.п. Ход экспериментов и цифры — в `notebooks/02_experiments.ipynb`.
- **Формат ответа** проверяется `cg/submit.py` при записи (перечитывание файла строками, все `query_id`, ≤ 50 уникальных
  `item_id` из корпуса) и отдельно `scripts/validate_answer.py`.

| Шаг (Recall@50 на локальной валидации) | Recall@50 |
|---|---|
| BM25, топ-300 | 0,397 |
| + память кликов и добор по микрокатегориям | 0,405 |
| + бусты по локации, расстоянию и популярности | 0,602 |
| BM25 пул 1000 / 5000 с бустами | 0,707 / 0,770 |
| полный скоринг корпуса BM25 + e5-small | 0,822 |
| + центроиды локаций поиска из train | 0,848 |
| + реранкер LightGBM над топ-300 | 0,880 |
| + полное описание объявления в BM25 | 0,906 |
| + дообученный e5-small как второй энкодер (tau = 10) | 0,924 |
| + вес 2 у дообученного энкодера, пул 500 (первая стадия 0,908, Recall@500 = 0,973) | **0,928** |

### Какие типы ошибок нашёл при анализе и что с ними сделал

| Ошибка | Что сделал |
|---|---|
| Память кликов давала неверных кандидатов: тот же текст запроса в другой локации ведёт к другому исполнителю, а 90 % корпуса в train вообще не встречается | память убрана из первой стадии; популярность объявления оставлена как множитель и признак |
| Классификатор «запрос → микрокатегория» ошибается на 43 % новых запросов; как буст он вырезал релевантные объявления (−2 п.п.) | используется только как признак реранкера |
| У 16 % запросов не было центроида локации: локация поиска регионального уровня не встречается среди локаций объявлений, буст по расстоянию молчал | центроид считается по координатам объявлений, выбранных из этой локации поиска в train; покрытие 100 %, +2,6 п.п. |
| BM25 по первым 300 символам описания не находил объявления, у которых нужные слова стоят глубже (описания в среднем 900 символов) | индекс по полному описанию, +3 п.п. |
| Ограниченный пул: релевантное объявление в нужной локации стояло у BM25 на позициях 300–5000 и не доходило до буста | полный скоринг всех 189 212 объявлений на каждый запрос вместо пула, +7 п.п. |
| Дообученный энкодер при той же температуре, что у исходного, ухудшал слияние: его косинусы контрастнее | своя температура (10) и вес (2), оба энкодера вместе, +2 п.п. |
| Реранкер переобучался при росте модели (600–1500 деревьев, 63–127 листьев: −0,5…−1 п.п.) | 300 деревьев по 31 листу, min_child_samples 100 |
| Разрыв локальной и лидерборд-оценки (0,88–0,93 против 0,84–0,88) мог быть переобучением на признаки популярности | проверил: реранкер без признаков популярности и «виденности» теряет лишь 0,1 п.п., в том числе на запросах, чьё объявление не встречалось в train; значит, это сдвиг данных, порядок улучшений сохраняется |
| Ошибки формата, о которых предупреждает задание: id как числа, потеря ведущих нулей, дубли, индекс в csv | id читаются строками (`cg/data.py`), файл перечитывается и проверяется перед каждой отправкой (`cg/submit.py`) |
| Технический сбой: torch и LightGBM в одном процессе на macOS падают из-за двух копий OpenMP | эмбеддинги бенчмарка считаются в подпроцессе (`scripts/embed_bench.py`) |

Не помогло и не вошло: таблица переходов «локация поиска → локация объявления» как буст (−2 п.п.), символьный TF-IDF
как третий скор (−0,5…−1 п.п.), признаки памяти кликов и совпадения фильтров в реранкере (±0), параметры BM25 k1/b
и вес заголовка (±0), lambdarank вместо классификатора (−0,5 п.п.).

## Структура репозитория

```

  data.py, text.py           #   чтение parquet (id строками), нормализация и стемминг
  validation.py, metrics.py  #   сплит A/V, корпус валидации, Recall@k
  pipeline.py                #   шаблоны текстов объявления и запроса для BM25 и bi-encoder
  sources/bm25.py            #   BM25 (bm25s + Snowball)
  sources/dense.py           #   эмбеддинги sentence-transformers с кэшем, top-k
  sources/memory.py          #   память кликов и популярность (используются как признаки)

  fusion.py                  #   RRF-слияние списков (ранние этапы, notebooks/02)
  rerank.py                  #   признаки и LightGBM-реранкер
  submit.py                  #   сборка и строгая проверка answer.csv
scripts/                     # воспроизведение по шагам 01–07, validate_answer.py, embed_bench.py
experiments/                 # проверки гипотез на валидации и генераторы ноутбуков
notebooks/                   # 01_eda.ipynb, 02_experiments.ipynb (выполнены, с выводами)
release/                     # веса реранкеров (1 МБ), чтобы run.py работал без обучения
submissions/                 # answer.csv и все версии ответов
task/                        # условие задания (скриншоты)
data/, artifacts/            # данные и кэши (не в git): эмбеддинги, дообученная модель, пулы, логи
```

## Open-source модели и библиотеки

- `intfloat/multilingual-e5-small` (Hugging Face, лицензия MIT): bi-encoder для dense-поиска; веса скачиваются один раз,
  дальше всё офлайн. Его дообученная копия воспроизводится `scripts/04_finetune.py`.
- `bm25s`, `PyStemmer` (Snowball): BM25 и стемминг русского.
- `sentence-transformers`, `torch`, `datasets`, `accelerate`: инференс и дообучение bi-encoder.
- `lightgbm`: реранкер; `scikit-learn`: TF-IDF и логистическая регрессия классификатора микрокатегорий.
- `pandas`, `pyarrow`, `numpy`, `scipy`, `jupyter`.

Единственный источник обучающих пар и статистик — `train.parquet`. Ответы под конкретные `query_id` не подбирались,
тестовая разметка не восстанавливалась, внешние API не использовались.

## Что дальше

- Более длинный контекст для dense-модели (сейчас 128 токенов): полное описание в BM25 дало +3 п.п., описание явно недоиспользовано.
- Более крупные энкодеры (e5-base, bge-m3), дообучение с hard negatives.
- Больше обучающих запросов для реранкера (сейчас 8 000).
- Жёсткие ограничения из фильтров запроса: «Тип услуги …» совпадает с параметрами объявления в 99 % кликов.
